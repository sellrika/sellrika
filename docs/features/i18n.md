# Languages (i18n)

How the app's texts are translated: where they live, which language a visitor gets, and how to add a text or a language.

The app speaks English, German and Thai.

One dictionary serves the Bun server and the Vue frontend.
So a text is translated once and shows the same everywhere:

- the staff pages
- the storefront
- validation messages
- service errors
- receipts
- emails

## Where the texts live

| File | What |
|---|---|
| `i18n/en.ts` | English. It is the source of truth. Every key is here. |
| `i18n/de.ts` | German. `satisfies Record<keyof typeof en, string>` makes a missing or extra key fail the type check (`bun check`). |
| `i18n/th.ts` | Thai. The same `satisfies` check as German. |
| `i18n/index.ts` | `Locale`, `LOCALES`, `DEFAULT_LOCALE`, `Key`, `translate(locale, key, params)`, `negotiate(acceptLanguage)`, `isLocale()`, `shopLocales()`, `extend()` |

### Keys

- Keys are flat and dotted: `<area>.<what_it_says>`.
  Examples: `orders.refund`, `validation.name_required`, `common.save`.
- Placeholders are `{name}`. They are filled from `params`:
  `t("common.page_of", { page: 1, pages: 3 })`.
- Never build a sentence from translated pieces. Use one key with placeholders.
- Plurals are two keys.

### Alias

The alias is `@i18n`. It is in both `tsconfig.json` and `vite.config.ts`.

### Words of an add-on

`extend(locale, words)` in `i18n/index.ts` adds words to one language.
An add-on with its own dictionary uses it. A key the app already has is replaced.

## Which language a visitor gets

`I18n.localeOf(req)` in `app/xcore/i18n/I18n.ts` decides, in this order:

1. The `lang` cookie, when set (`LOCALE_COOKIE` in `app/constants/Locale.Constant.ts`).
2. The best `Accept-Language` match.
3. English.

### Inside a request

- The router runs every handler inside `I18n.withLocale(locale, …)`. That is an `AsyncLocalStorage`.
- So any code the request awaits can call `t()` without a request being passed around: validators, services, repositories, mail templates.

### Outside a request

- In a cron job or the reconcile job, `t()` is English.
- A job may wrap itself in `I18n.withLocale(savedLocale, …)` to use another language.

### On the online store

The language must be one the shop offers (`shops.languages`, first = default).

- `I18n.localeOf(req, allowed)` takes that list.
- The cookie counts only when it is in the list.
- `negotiate(header, allowed, fallback)` picks among the list.
- The fallback is the shop's default.
- Once the store's shop is known, `I18n.narrow()` changes the running request's language.
  The `AsyncLocalStorage` holds a small box, so it can be changed.

More in [online-store.md › Languages](online-store.md#languages).

### The switcher

`POST /lang { locale }` (`LocaleController`, public, no auth):

- sets the cookie for a year (`LOCALE_COOKIE_DAYS` = 365)
- goes back to the page

Where it sits:

- In the staff app's user menu: Language → English / Deutsch / ไทย.
- In every storefront footer. It shows only the shop's languages. It is hidden when there is one.

## Using it

### Frontend

```ts
import { t } from "@/lib/i18n";
```

- On a staff page, it reads the `locale` shared prop (`SharedProps.locale`, on every Inertia page). So it is reactive and SSR-safe.
- On a store page, it reads `locale` and the words from the page's data island (`#store-data`).
- `locale()` gives the code for `Intl`. `lib/format.ts` formats money and dates with it.
- Call `t()` at render time, never at module load.

The browser downloads one language only:

- `resources/js/app.ts` loads the page's `i18n/<locale>.ts` as its own file before Inertia shows a page. That is true for the first page too.
- After a language switch, it loads the new one.
- Never import `@i18n` as a value in browser code for `translate()`. It holds every language.
- The server keeps all languages.

### Backend

```ts
import { t } from "@xcore/i18n/I18n";
```

Use `I18n.current()` when you need the code itself.

### Validators

- A zod custom message is a dictionary key: `z.string().min(1, "validation.name_required")`.
- `validate()` translates known keys.
- It hands Zod's own messages ("Too big…", "Invalid email") to Zod's `en` / `de` / `th` locale.
- So a message that only restates a Zod default is not needed.

### Shared code

Some code runs in the browser and on the server: `app/validators/StoreCustomer.Validator.ts`, `app/helpers/*`.

- It must not import `@xcore/i18n/I18n`.
- It returns keys (`Key`) and params.
- Each side translates.

### Emails

- The classes in `app/emails/` build the texts with `t()` when they are sent.
- An order email is in the buyer's language. That is the language of the checkout's request.
- The reconcile job replays the locale saved on the cart snapshot.

### The page language

`<html lang>` follows the locale (`app.edge`).

## Extensions

Each extension has its own `i18n/` folder: `extensions/<key>/i18n/en.ts`, `de.ts`, ….

The host:

- reads every file
- translates the manifest's texts
- gives listeners and routes `t`
- gives browser scripts `api.t`
- shows a `GatewayError` translated, when its message is a key

A new language for an extension is one more file there.

More in [extensions.md](extensions.md) › Languages.

## Adding a text

1. Add the key to `i18n/en.ts`, `i18n/de.ts` and `i18n/th.ts`. The type check tells you when one is missing.
2. Use it: `t("area.key")`.

## Adding a language

1. Add it to `Locale` and `LOCALES` in `i18n/index.ts`.
2. Write a new `i18n/<code>.ts`.
3. Add it to `dictionaries` in `i18n/index.ts`.
4. Add the Zod locale in `app/validators/validate.ts`.
5. Add the `lang.<code>` key in every dictionary. It is the language's own name.

The extensions do not need a file for it.
A language they do not ship falls back to their English.
